# Technical Decisions and Tradeoffs

This document exists so the project can be shown on a resume/GitHub honestly — documenting what was deliberately cut and why is itself a signal of engineering maturity, and it's also just true: every decision below was made to protect the 45-day DSA-learning goal, not because of a technical limitation we couldn't work around.

*A naming note, since this log is chronological: the project was built under the working name "Traceviz" and later renamed to **Codeloupe**. Entries below use whichever name was current at the time -- left as-is rather than rewritten, since this document's whole point is an honest record of what actually happened, not a cleaned-up retelling. "Milestone" section headers likewise refer to the original build-phase plan (see `development-roadmap.md`), not the shipped product's current structure.*

## What we are explicitly not building, and why

**Auth, accounts, multi-user support, cloud deployment.** This is a single-user local tool for 45 days of personal study. Adding real authentication and a production deployment is legitimate work, but it has zero relationship to whether you learn recursion — it's real effort competing directly with study time for no learning payoff. If a public version is ever wanted, it's a clean, well-scoped follow-up project after Day 45, not a day-1 requirement.

**A hardened, multi-tenant-safe code execution sandbox.** The execution model (subprocess, timeout, resource limits, no network) is appropriate for "don't let my own typo hang the app," not for "defend against a hostile stranger's exploit." Building genuinely hostile-input-safe sandboxing (containerization, seccomp, gVisor-style isolation) is a deep, separate discipline that would consume real build time for a threat model that doesn't apply here — you're the only user, running your own code.

**A general-purpose "visualize any Python value" engine.** The trace visualizer renders specific, known data-structure shapes (arrays, linked-list nodes, call stacks, trees, graphs, DP tables) that are pattern-matched from `step.locals`, not a universal object visualizer. A fully general version is a much harder and more open-ended engineering problem, and the curated version covers 100% of what the curriculum actually needs.

**A from-scratch Python interpreter or custom execution engine.** `sys.settrace` plus subprocess isolation does everything the tracer needs. Writing a toy interpreter is a fun, legitimate project — just a different one, with essentially no DSA-learning content.

**Bulk-importing hundreds of problems.** The starter bank (~90-95 problems, see `problem-roadmap.md`) is hand-curated to match the curriculum's actual patterns. A bulk import would dilute quality and curriculum-fit for a beginner on a deadline, and volume was never the bottleneck — pattern coverage was.

**A high-fidelity conversational mock-interview AI.** Mock-interview mode (`PART 11`) is deliberately a focused, minimal-UI feature: timer, problem, editor, structured post-submission review. A fully conversational interviewer that asks natural follow-ups and reacts to hesitation is a much bigger product in its own right and risks becoming the interesting-to-build distraction the whole project is designed to avoid.

**Excessive gamification.** No points, badges, streak rewards, or leaderboards, per your explicit instruction. The dashboard's only job is showing you the truth about where you're weak.

**Advanced DSA topics beyond the 45-day scope** (segment/Fenwick trees, tries, union-find, Bellman-Ford/Floyd-Warshall/MST, bitmask/digit DP, advanced string algorithms). These are genuinely good topics — just not ones a placement-focused beginner needs inside 45 days, per the curriculum's stated priority of depth over breadth (see `50-day-curriculum.md`'s coverage summary).

## Honest framing of the complexity estimator

The estimator produces a **complexity estimate**, combining a structural (AST-based) signal and an empirical (benchmark-based) signal — never a mathematically authoritative Big-O determination. This distinction is enforced in the product's actual language, not just in this doc:

- Say: *"Implemented heuristic structural and empirical complexity estimation, combining AST-based static analysis with curve-fit runtime/memory benchmarking."*
- Never say: *"AI automatically determines Big-O"* or any phrasing implying the tool proves complexity rather than estimating it.

The limitations are real and worth stating plainly: the structural analyzer can be fooled by code whose real cost doesn't match its loop-nesting shape (e.g., an early-exit condition that changes measured complexity depending on input distribution, or a huge constant factor that looks like a different growth curve at small n); the empirical benchmark is only as good as the input sizes it's tested against and can misclassify a curve near the boundary between two growth shapes. The two signals are shown side by side specifically so that *you* reconcile them and justify your own answer — which is a more accurate simulation of what an interviewer actually asks for than a single "trust me" number would be.

## What's deferred to after Day 45

Anything in this list is a reasonable next step once placement-readiness is achieved, deliberately not attempted during the 45 days: authentication and a real deployment; a broader problem bank (hundreds of problems instead of ~90-95); the general-value visualizer; a more sophisticated spaced-repetition algorithm (e.g., full SM-2) instead of the simple adaptive ladder in `problem-roadmap.md`; a richer mock-interview experience; mobile support; multi-device sync.

## Milestone 1 build note: Monaco is bundled locally, not CDN-loaded

`@monaco-editor/react` defaults to fetching the Monaco editor from `cdn.jsdelivr.net` at runtime. During Milestone 1 this failed outright in the build/test environment (the CDN wasn't reachable), which forced a small, concrete implementation decision: bundle `monaco-editor` as a direct npm dependency and wire its web worker through Vite's native `?worker` import instead of the library's default loader. This isn't a compromise -- a locally-bundled editor is arguably the more correct choice anyway for a tool meant to run offline on your own machine for 45 days, so it's being kept even though the specific failure that surfaced it was environment-specific. Full detail and the exact (non-obvious) import path Monaco's package `exports` map requires is documented in `frontend/src/monacoSetup.js`.

## Phase 1 pivot, then expansion: 32 problems -> 76 problems across 3 tiers

The original `problem-roadmap.md` sketch (written pre-implementation) targeted ~90-95 problems. The first shipped cut, once the plan changed to "finish a usable app before the Claude subscription ends," was a deliberately smaller **32 problems** -- reasoning documented in the git history of this section: getting one problem to full bar (hand-written description, constraints, starter code, verified reference solution, edge-case notes, 3 real hints, auto-verified test cases) is real work, and 32 was judged a higher-value use of limited time than a larger but thinner set, while every one of the 15 requested interview patterns still got at least one Easy-before-Medium pair.

That 32-problem set was then deliberately expanded to **76 problems**, organized into three explicit tiers (`problems.path_tier` in the schema) once core learning-platform functionality was verified end-to-end and the user asked for a more substantial bank without diluting curation quality:

- **Core 45-Day Path** (51 problems, `path_tier='core'`, each tied to a specific curriculum `day`) -- the required path. Primarily Easy/Medium. Completing this is the "job-ready" bar; the dashboard's Core Path progress bar tracks against this count specifically, not the full 76.
- **Extended Practice** (19 problems, `path_tier='extended'`, `day=NULL`) -- additional curated Easy/Medium problems for reinforcement and weak-topic practice. Explicitly optional; never required within the 45 days.
- **Advanced Challenges** (6 problems, `path_tier='advanced'`, `day=NULL`, all Hard) -- curated for genuinely high-value advanced interview patterns (Trapping Rain Water, Median of Two Sorted Arrays, Merge k Sorted Lists, Serialize/Deserialize Binary Tree, Word Ladder, Edit Distance), one per topic area that was thinnest at the Hard level. Strictly optional, never gates Core Path completion, and the UI (tier badges, dashboard, problem browser sections) is explicit about that distinction throughout.

The expansion specifically targeted the previously-disclosed gap: heaps went from 2 problems to 5 (adding Last Stone Weight, K Closest Points to Origin, Kth Largest Element), graphs from 2 to 8 (adding Flood Fill, Rotting Oranges' multi-source BFS, Course Schedule's cycle detection, Pacific Atlantic's dual-BFS). Every new reference solution was verified twice, independently: once standalone before being written into `seed_problems.py`, and once again through the live grading API after seeding (`verify_all_live.py`) -- the same two-pass process that caught the `json.dumps`-vs-`repr` and in-place-mutation bugs described elsewhere in this file. Remaining thin spots, disclosed honestly rather than glossed over: `queues` and `strings` each have only 1 dedicated problem (most queue/string-heavy patterns are covered under `sliding-window`, `two-pointer`, and `arrays` instead, which is a reasonable categorization choice but does mean those two topic labels look sparse in isolation).

See `problem-roadmap.md`'s "Actual implementation" section for the full per-topic/per-tier/per-difficulty breakdown, the reference frameworks used (NeetCode 150, Striver's sheet, LeetCode citations), and the trace-visualizer fix this expansion prompted (see the entry below on tracing incorrect code).

## Second problem-bank expansion: 76 -> 109 problems, with a mandatory cross-bank dedup review

A second expansion targeted the specific gaps the first expansion disclosed rather than being an across-the-board increase: `queues` and `strings` topics were thin (1 problem each), and `sliding-window`/`two-pointer` had shallow Easy-to-Medium progressions. Before any of the 33 candidate problems were written into `seed_problems.py`, a deliberate deduplication pass checked every candidate against the *entire* existing 76-problem bank (not just its own topic), specifically to catch three failure modes: an outright duplicate, a duplicate under a different name, and a problem teaching essentially the same pattern with no meaningful variation.

This caught two real issues before they shipped: a candidate `valid-anagram` (Easy, strings) turned out to already exist in the bank under the exact same slug -- an easy miss, since it's exactly the kind of "obvious first Easy problem for a thin topic" both an independent planning pass and the existing bank would naturally converge on. And two candidate queue problems (`moving-average-from-data-stream` and `number-of-recent-calls`) were mechanically near-identical (both: append to a deque, evict stale entries from the front) with the only real difference being a fixed-count window versus a time-bounded one -- only the more distinctly valuable one (time-windowed rate limiting) was kept. Both fixes are documented in detail, with the full per-problem justification for every one of the 33 survivors, in `problem-roadmap.md`'s "Second expansion" section.

The same two-pass verification process as the first expansion applied again: every reference solution was checked standalone before being written into the seed file, then re-verified through the live grading API (`verify_all_live.py`) after seeding -- 109/109 passed. Final tier split: Core 59 / Extended 39 / Advanced 11. Final difficulty split: Easy 35 / Medium 63 / Hard 11 (Hard remains 100% confined to the Advanced tier). Every topic in the bank now has at least one Easy and one Medium problem, closing the queues/strings gap disclosed at the end of the first expansion.

## The trace visualizer must stay useful for INCORRECT code, not just correct solutions

This is Traceviz's core differentiator, restated because it drove a real fix: the tracer shows what the learner's OWN code actually does, bugs included -- not a canned animation of a correct algorithm. Two bugs meant this wasn't actually true before this pass:

1. **A crashing submission lost its entire trace.** The original harness wrapped `exec()` in a bare `try/finally` with no `except` -- if the submitted code raised (an `IndexError` from bad array logic, a broken linked-list pointer, anything), the exception propagated straight past the `print()` calls that emit the trace payload, so the parent process saw a bare crash with zero steps. A learner's buggy code -- exactly the case Traceviz should be most useful for -- showed nothing. Fixed by wrapping `exec()` in `try/except Exception`, capturing type/message/line, and still printing every step captured before the crash. A related, more subtle issue: Python's trace protocol sends a synthetic "return" event (with `arg=None`) to every frame as it unwinds during an exception, which would have shown every function on the call stack as "returned None" right as the program crashed -- misleading in a debugger built to show truth. Fixed by tracking the "exception" event (which fires immediately before each of those synthetic returns) and suppressing the fake return step for that frame specifically. Verified via a standalone `sys.settrace` reproduction before touching the real harness (see `execution/tracer.py`'s module docstring and inline comments for the full reasoning).

2. **An infinite loop silently threw away everything already captured.** The `MAX_STEPS` guard called `sys.settrace(None)` and returned, which stops recording new steps but does NOT stop the loop itself -- it kept running, untraced, until the sandbox's wall-clock timeout eventually killed the whole process, discarding the already-captured steps along with it (they were never printed). Fixed by raising a custom exception from inside the trace function itself once the limit is hit, which unwinds `exec()` immediately (verified this actually works via a standalone reproduction -- it's a documented but non-obvious property of `sys.settrace`) instead of letting the loop run to the wall-clock timeout. In practice this converts almost every infinite-loop case from "steps lost, timeout" to "steps preserved, fast, clearly labeled as truncated."

3. **"Trace my code" traced nothing meaningful for the primary intended workflow.** Problem starter code is just a bare function signature (e.g. `def two_sum(nums, target):\n    pass`) -- a learner writing only the function body and clicking "Trace my code" was tracing a script that never actually CALLED the function, so the trace showed the `def` statement and nothing else. Fixed by adding `/api/problems/<slug>/trace`, which appends a real call to the learner's function using one of the problem's own stored test cases (`fn_name(*args)`, embedded via `repr()` for the same JSON-true/false/null-safety reason as the grading harness) before tracing -- so the button works out of the box without requiring the learner to hand-write their own driver/print statement first. The generic `/api/trace` endpoint (no test-case injection) is kept as-is for the Scratchpad, where there's no associated problem to pull a test case from.

The tracer's return value now includes a `status` field with five distinct values (`completed`, `runtime_error`, `truncated`, `syntax_error`, `crashed`) so the frontend can show a clear, honest banner instead of a generic pass/fail -- see `execution/tracer.py`'s module docstring for exactly what each one means and `TraceViewer.jsx`'s status banner for how it's surfaced. All five were exercised deliberately with intentionally-broken submissions (wrong array indexing, a linked-list reversal that overwrites `.next` before saving it, unbounded recursion, an infinite `while True`) both directly against `trace_code()` and through the full browser E2E suite before considering this done.

## Data-structure-aware visualizations (Phase 3 → now built): 9 specialized views on top of the generic tracer

The generic step-through tracer (locals table + the old crude "any list becomes boxes" array view) was always accurate but never actually *explained* anything -- it showed raw values, not the shape of what was happening. This phase adds 9 specialized, data-structure-aware visualizations (`frontend/src/components/Visualizers/`) that render the learner's actual captured execution state as the structure it represents: an array/string with pointer and sliding-window highlighting, a real linked-list node-and-arrow diagram, a live recursive call stack, an actual tree diagram, a stack/queue view, sorting bars, a grid or node graph view, a binary-heap tree, and a DP table with change-highlighting.

**Same core principle as the tracer itself, restated for every one of these views:** each one renders the learner's OWN captured execution snapshot -- never a canned "what the correct algorithm does" animation. None of the view components know what the correct answer is; they only know what the trace actually recorded. This is why the same views work identically for correct and buggy submissions -- verified explicitly, per view, with both (see `e2e_visualizers_test.py`, 16/16 checks passing, covering every one of the 9 categories with at least one buggy submission: a wrong-answer sliding window, a linked list that reverses into a self-cycle, unbounded recursion, an off-by-count island counter, and a clone-graph missing its visited map).

**Backend enrichment this required (`execution/tracer.py`):** two additions, both necessary for the specialized views (not the generic tracer, which didn't need them):
1. **Stable object identity (`__id__`).** Every custom-object snapshot (`Node`, `TreeNode`, `GNode`, ...) now includes `"__id__": id(v)`. Without this, two local variables pointing at the *same* underlying node (e.g. `prev` and `curr` in a linked-list reversal) would serialize as two independent, duplicate-looking JSON trees with no way to tell they're the same object -- exactly the information a learner needs to see ("your `prev` and `curr` are pointing at the same node right now"). The frontend's `nodeGraph.js` deduplicates by `__id__` across every local to build one shared node/edge graph instead of several disconnected copies.
2. **`collections.deque` support.** `deque` has no `__dict__` and wasn't a `list`/`tuple`/`dict`/`set`, so it fell through to a bare `repr()` string (`"deque([1, 2, 3])"`) -- useless to a queue/BFS visualizer. It's now serialized the same way as a list. This matters throughout the curriculum: BFS frontiers, `sliding-window-maximum`'s monotonic deque, and any queue-shaped problem all use `deque`, not a plain list.

**Detection is structural first, topic-assisted second** (`Visualizers/detect.js`): an actual node-graph shape found in the data (tree/linked-list/graph, distinguished by whether the node has `left`/`right`, `neighbors`, or `next`) always wins, since that's unambiguous regardless of what problem is being traced. Failing that, the problem's own `topic` metadata combined with a matching data shape picks one of: DP table, heap, sorting bars, grid, stack, queue -- and a generic array/string/pointer view is the catch-all fallback for everything else (arrays, strings, hashing-with-arrays, binary-search, two-pointer, sliding-window). A live recursive call stack is shown *additionally*, alongside whatever primary view applies, whenever the trace shows genuine recursion.

**A real false-positive caught during verification, worth recording:** the first cut of "is this recursion?" simply counted how many times each function name appeared in a `call` event, but building a 5-node linked list calls `Node.__init__` five times too -- an ordinary loop, not recursion, and it was spuriously triggering the call-stack view on every linked-list problem. Fixed by tracking the actual active call stack and only flagging recursion when a function name reappears while an earlier call to that *same* function is still on the stack (i.e. a function genuinely calling itself), which correctly distinguishes "called sequentially in a loop" from "calls itself."

**Grid detection needed to be broader than "numbers."** `number-of-islands`' stored test data represents grid cells as the strings `"1"`/`"0"`, not integers -- the first cut of grid detection (numbers/booleans only) silently missed it. Grid detection now accepts any row of short scalar values (number, boolean, or a string up to 3 characters), while DP-table detection stays strictly numeric/boolean so a char-grid problem never gets misdetected as a DP table.

**Explicitly out of scope, per the "don't build a universal visualizer" instruction:** arbitrary user-defined classes with no recognizable shape, adjacency-list-only graphs (dict-of-lists rather than actual node objects, e.g. `course-schedule`), and anything nested more than a few levels deep. These fall back to the generic locals table, which was always there and stays accurate regardless.

## Learning-loop features: integrated into the existing trace/test/attempt architecture, not bolted on

Seven features were added directly on top of infrastructure that already existed, specifically so the product stays "Write code -> run -> test -> trace -> understand" rather than growing into a pile of disconnected tools:

- **Predict -> Run -> Compare** (`TraceViewer.jsx`'s `PredictPanel`): optional, off by default. The learner free-text-predicts what the *next* traced step does; revealing shows a structural diff (`utils/compare.js`'s `diffLocals`) of what actually changed. Never auto-grades the free text -- there's no reliable way to score "left will move to index 3" against an arbitrary trace event, so the learner judges their own guess.
- **Failure analysis** (`ProblemWorkspace.jsx`'s `FailureAnalysis`): surfaces the *first* failing test case (not a wall of red) with expected vs. actual and a purely structural mismatch description (`describeMismatch` -- length differences, which indices differ, type mismatches) that never claims to know the root cause. A one-click "inspect this case in the Trace tab" jump opens the Trace tab at the same test case and lands on its final step; this only works because `run_problem` and `get_problem`'s test-case queries both `ORDER BY id`, so a failing result's index reliably lines up with the same case in `visible_test_cases`.
- **Pattern-recognition practice** (`PatternPractice`): collapsed by default, above the editor. Guess a pattern category from a fixed list; reveal shows `problem.pattern` (and `optimal_approach`) side by side with the guess. The guess is never auto-graded right/wrong -- it's a self-comparison, and revealing requires a guess first so it can't become an accidental spoiler.
- **Custom test-case playground** (Playground tab): the "enter my own input -> run -> trace -> inspect" loop the user asked for, built as a thin variant of existing infrastructure rather than new sandbox code. Backend: `POST /run-custom` calls the exact same `test_runner.run_against_tests` harness with one `{"args": ..., "expected": None}` case (ungraded -- no pass/fail, just actual output or error); `/trace` gained an optional `custom_args` field as an alternative to `test_case_index`. Edge-case preset buttons are derived from the SHAPE of the problem's own first example (a list gets empty/single/duplicates/negative presets, a string gets empty/single-char, a number gets zero/negative/boundary) rather than a fixed generic list, so the suggestions are actually relevant and stay small (never more than 4 buttons).
- **Attempt history / solution journey** (History tab): `GET /api/problems/<slug>/attempts` is a pure read view over the `attempts` table `log_attempt` already wrote to every run -- no new tracking was added. Shows each attempt's result, hints used, solution-revealed flag, time taken, and the submitted code itself (already stored).
- **Compare approaches / complexity**: folded into the History tab rather than built as a separate page, since it needs exactly the historical-code data attempt history already surfaces. A per-attempt "compare complexity to current code" button re-runs the existing `complexity-estimate` endpoint against that attempt's stored code alongside the current editor content -- no new estimation logic, and it inherits the existing structural-vs-empirical distinction rather than inventing a new confidence claim.
- **Explain-your-thinking**: optional, entirely client-side (no schema change, no persistence) -- a plan written before running, compared against the problem's real pattern and (if already computed) estimated complexity after. Deliberately ephemeral: it's interview-prep reflection, not a tracked metric, and persisting it would have meant a migration for something the user explicitly said should not be required per problem.

**Deferred, with reasoning given to the user rather than silently skipped:** mistake-journal classification, pattern-level (as opposed to topic-level) revision tracking, and an adaptive "today's session" recommender. All three need real new schema and, for the mistake journal specifically, a confidence-tagging design (`likely` vs `user-confirmed` vs `manually selected`) that's easy to get wrong in a way that overclaims automated accuracy -- exactly what the user's own spec warned against. The latter two also structurally depend on the mistake journal existing first to be pattern-aware rather than a rehash of the topic-level `top_weaknesses` breakdown `/api/progress` already provides. Building three more speculative subsystems in the same pass as everything above risked exactly the "collection of random tools" feel the user said the final product should avoid.

All seven were verified end to end (`e2e_learning_features_test.py`, 27/27 checks) against both correct and intentionally wrong/crashing submissions -- not just the happy path -- with zero console errors, and the full existing regression suite (backend endpoints, live grading verification, general E2E, visualizer E2E) re-run clean afterward.

## Mistake journal, pattern-level revision, and adaptive practice sessions: one connected system, not three widgets

These were originally deferred (see the section above) because they needed real schema and a confidence-tagging design, not a bolt-on. Built as one pipeline: **attempts -> observed outcomes -> mistake journal -> pattern/topic weaknesses -> revision schedule -> Today's Session recommendations**, reusing every existing piece of that chain rather than duplicating it.

**Mistake journal (`logic/mistakes.py`, the new `mistakes` table -- replacing the never-wired-up `mistake_patterns` stub that had sat unused in the schema since an early planning pass).** One row per FAILED attempt, created automatically at `log_attempt` time from a `failure_context` the frontend builds out of the `/run` response it already has (no extra request). The classifier is deliberately conservative about confidence: it NEVER assigns the top-tier `observed_confirmed` level to a category -- mapping an exception type or a failing input's shape onto one of the ten named categories is always an inference, so the automated classifier's ceiling is `likely_issue`, always paired with the concrete evidence that produced it (the exact exception message, or which input failed). When no rule confidently applies -- e.g. a wrong answer on ordinary-shaped input that fails some but not all cases, with no exception -- the mistake is stored as `unclassified` rather than guessed at, exactly per the instruction that unclassified beats inaccurate. `user_confirmed` and `manually_selected` only ever come from the learner reviewing a suggestion in the UI (`MistakeSuggestion` in `ProblemWorkspace.jsx`) or picking their own category outright; the classifier is never re-run over a human's answer. Verified explicitly: a clear `IndexError` correctly suggests "Off-by-one errors"; a genuinely ambiguous partial failure (passes 3 of 4 cases, fails one non-edge-shaped case with no exception) correctly stays unclassified rather than guessing.

**Pattern-level revision (`logic/pattern_families.py`).** `problems.pattern` turned out to be far too fine-grained to aggregate on directly -- 107 distinct strings across 109 problems, almost all singletons ("Floyd's slow/fast pointer", "fast/slow + reversal", and "fast/slow pointer" are three different strings for what's really the same technique family). A raw `GROUP BY pattern` would have made pattern-level tracking useless. Added a small ordered rule table (topic + keyword-in-pattern -> family name, e.g. "Fast/slow pointers", "Sliding-window boundaries", "Tree DFS recursion" -- the user's own example families) instead of a hardcoded per-problem lookup, specifically so it keeps working as new problems are added without a manual entry for each one; falls back to `General <topic>` when no family confidently applies rather than forcing a fake grouping. This buckets the 107 raw patterns into 41 real families, several with genuine multi-problem membership. Surfaced as `pattern_weaknesses` in `/api/progress`, alongside (never replacing) the existing topic-level `top_weaknesses` -- both are shown on the Dashboard.

**Adaptive "Today's Session" (`logic/practice_session.py`).** Combines up to 4 items -- a due revision problem, a problem tied to a *recurring* mistake (same pattern-family + category pair seen 2+ times, not a one-off), a problem targeting the single weakest pattern or topic, and a new Core-tier problem matching current progress -- each with a plain-language `reason` string so it's never a black box. Every signal is read from data the rest of the app already computes; nothing new is inferred here. Purely a suggestion list on the Dashboard: it never gates navigation, and the UI copy says so explicitly.

All three were verified together as one pipeline (`e2e_mistake_journal_test.py`, 19/19 checks): a classifiable failure, a genuinely ambiguous one that must stay unclassified, the confirm and manual-override review flows, the History tab and Mistake Journal page reflecting the final (human-reviewed) state, pattern weaknesses appearing on the Dashboard next to (not instead of) topic weaknesses, and Today's Session recommendations carrying real reasons. Full existing regression (backend endpoints, live grading, general E2E, visualizer E2E, prior learning-features E2E) re-run clean afterward.

## Approach comparison: my code vs a reference approach, built entirely on infrastructure that already existed

The last planned V1 learning feature: compare your own submission against a reference approach -- not just "here's the answer" but *why* it's better, with real numbers. Reuses three existing systems verbatim rather than building a fourth: `logic/analysis.py`'s `structural_estimate()` for the AST heuristic, `execution/sandbox.py`'s `run_code()` for actually running candidates, and `execution/tracer.py`'s `trace_code()` for both the operation-count signal and (from the frontend) "trace this approach," which just calls the existing `/api/problems/<slug>/trace` endpoint with reference code instead of the learner's -- no new tracing or visualization code at all.

**A pre-existing naming bug got fixed along the way.** `problems.brute_force_reference` had held the OPTIMAL solution the whole time -- it was the same source used to auto-compute every problem's expected test outputs at seed time (`init_db.py`'s `_compute_expected_outputs`), just stored under the wrong name, and `/api/problems/<slug>/solution` had been serving it as `solution_code` under that same wrong name since the Hints tab's solution reveal was built. Renamed to `optimal_reference` (schema + seed data + the one `app.py` read site); `brute_force_reference` now means what its name says.

**Only 13 of 109 problems have a real brute-force baseline, deliberately.** Writing a distinct, correct, meaningfully-worse-complexity implementation for every problem would mean either a huge amount of new authored code or fabricating naive alternatives that aren't actually useful -- exactly what the user's own instructions warned against ("do not pretend every problem has one universal best approach," "only where technically valid and genuinely useful"). Picked 13 spanning three situations verification specifically needed to cover: naive-but-improvable (`two-sum`, `contains-duplicate`, `valid-anagram`, `maximum-subarray`, `best-time-to-buy-sell-stock`, `group-anagrams`, `longest-unique-substring`, `majority-element`, `single-number`, `3sum` -- nested loops or sorting where a hashmap/two-pointer/counting trick wins), a real growth-class trade-off (`climbing-stairs` -- exponential recursion vs. linear DP), and linear-vs-logarithmic search (`binary-search`, `search-rotated-sorted` -- a genuinely valid "brute force," not a strawman). Every other problem (`valid-parentheses`, `reverse-linked-list`, etc.) has no baseline on file, and the comparison UI degrades to "your code vs. the optimal reference" rather than inventing one or hiding the feature entirely. Each baseline's correctness was checked twice before being trusted: once offline against the seeded test cases during authoring, then permanently via `verify_approach_baselines.py`, which submits the actual stored source through the live grading API (same discipline `verify_all_live.py` already applies to every `optimal_reference`) and confirms every growth-curve generator produces a real, non-timed-out measurement at every declared size.

**Growth-curve benchmarking reuses the `has_stress_test`/`stress_test_generator` columns' *idea*, not the columns themselves.** Those were reserved for a different, still-unbuilt feature (randomized differential correctness testing against a reference) and repurposing them for benchmarking would have quietly foreclosed that later feature and mislabeled what the columns mean. Added `growth_curve_generator` (a `generate(n) -> args` function, only set alongside `brute_force_reference`) and `growth_curve_sizes` (a hand-picked JSON array of sizes per problem -- `[10, 20, 30]` for `climbing-stairs`' exponential recursion, `[10000, 100000, 1000000]` for the O(log n) searches, everything else in between) instead, and left the original two columns untouched for whenever that other feature gets built.

**Every number is labeled with exactly where it came from**, matching the explicit "clearly distinguish empirical measurements from structural/AST-based estimates" and "do not overclaim complexity results" instructions: `structural` (AST-shape heuristic, no code ever runs, same caveat text as the Complexity tab), `empirical_existing_tests` (real wall-clock time + peak memory via `resource.getrusage(RUSAGE_SELF)` inside the sandboxed subprocess, but only at whatever sizes the problem's own seeded tests happen to use), `growth_curve` (real measurements at synthetic sizes -- a timed-out size is reported as exactly that, "became impractical here," never silently dropped or faked), and `operation_count` (a real count of trace steps for one representative input, not an estimate, explicitly caveated as specific to that one input's size). Peak memory is read from inside the child process itself via a small harness injection (the same pattern `empirical_timing` already used for timing), not from the parent's `getrusage(RUSAGE_CHILDREN)` -- that call is a monotonic high-water-mark across everything the Flask process has ever spawned, which would have made later, smaller runs falsely report an earlier run's peak. A crashing or infinite-looping candidate degrades to an honest per-size/per-candidate gap (`{"seconds": null, "timed_out": true}`) rather than taking the whole comparison down -- verified directly by comparing against literal `while True: pass`.

**Two-stage reveal, deliberately mirroring the Hints tab's existing "reveal solution" gate** rather than inventing a second reveal mechanism: `POST /approach-comparison` with `reveal_code=false` (the default, and all the "Compare my approach" button ever sends) returns every number for every candidate but never the reference source -- the numbers alone are the pedagogical payload, they explain *why* without handing over *what*. `reveal_code=true` (a separate explicit "Show reference code" click) additionally returns the source and sets the same `solutionRevealed` flag the Hints tab uses, so an attempt logged after seeing reference code is tagged assisted either way, with no gap between the two reveal paths. On the frontend, the whole tab additionally stays gated behind having run at least once (`!runResult` shows a plain explanation instead of a button) -- not full success, since the naive-baseline use case specifically needs to work on a first, unoptimized attempt.

Verified end to end (`e2e_approach_comparison_test.py`, 17 checks) across the three situations the feature was built for: `two-sum` submitted as brute force (three-way comparison, a growth curve that actually shows O(n^2) diverging from O(n), gated reveal, "trace this approach" showing the reference's own execution), `valid-parentheses` submitted already-efficient (graceful two-way degradation, no fabricated baseline), and `climbing-stairs` submitted as naive recursion (the trade-off case). Full existing regression (backend endpoints, live reference-solution verification, the new baseline verification, general E2E, visualizer E2E, learning-features E2E, mistake-journal E2E, the 4-variant central-workflow E2E) re-run clean afterward.

## Codeloupe: rebrand, visual identity, and an IA/UX pass across the real app

V1's feature set was locked (see the sections above) before any of this started, per explicit instruction: rebrand and UI/UX polish only after the approach-comparison feature, with no new functionality riding along. Two rounds of visual-identity review happened outside the codebase first (three sketched directions, then a refined v2 combining the reviewer's preferred direction's dark developer-tool foundation with one deliberately-scoped idea borrowed from a rejected direction) before anything here was touched -- this section covers only the approved result and what changed in the actual app to realize it, plus the separately-scoped IA/UX audit that came with it.

**Two accents, two jobs -- enforced as a hard rule, not a style suggestion.** `App.css`'s `:root` defines `--teal` (brand, navigation, primary actions, progress) and `--amber` (the thing currently being inspected -- the active trace step, the executing line, a focused input, keyboard focus) as the only two colors allowed to carry either meaning anywhere in the app. Auditing the pre-existing stylesheet found real collisions this rule had to fix: `in_progress` status badges, `Important`/`Medium`-tier badges, and several visualizer "just changed" highlights were all using amber-adjacent ad-hoc hex (`#f0c060`) for meanings that had nothing to do with focus, which would have made the real focus signal (the trace scrubber, the active line) less legible by drowning it in noise. Fixed by adding a separate categorical family for everything else -- `--violet`/`--sky`/`--orchid` for tier/status metadata, `--caution` (a visibly different, more muted orange) for anything that previously leaned on amber for "warning" or "in progress," `--ok`/`--err` for pass/fail. The qualitative pointer-identity palette in `detect.js` (the hash-based color a trace visualization assigns to each tracked variable name) was also audited and rebuilt to exclude both teal and amber outright, so a pointer variable can never randomly render in a color that falsely claims to be a button or a focus indicator.

**The trace scrubber is where the focus-ring identity becomes an actual interaction, not just a badge color.** The native range input (`.trace-scrubber` in `App.css`) is restyled so the filled track (steps already visited) uses a dim teal and the thumb -- the current step -- is amber with the same soft halo used for keyboard focus everywhere else in the app; the fill percentage is set from React via a `--scrub-pct` custom property computed from the current step index. The same "amber = the direct result of the step you're looking at" rule was carried through every specialized visualizer (`visualizers.css`): a just-swapped sort bar, a freshly-written DP cell, the currently-executing call frame, a tracked grid cursor. Structural anomalies (a linked-list cycle, an orphaned node) stayed on `--caution`/`--err` instead, since those are correctness warnings, not "look here right now" -- collapsing the two would have diluted the one meaning amber is supposed to carry.

**Navigation order was reconsidered, not just relabeled.** Was Curriculum -> Problems -> Dashboard -> Mistake Journal -> Scratchpad (Curriculum as the default route); became Dashboard -> Curriculum -> Problems -> Mistake Journal -> Scratchpad, with Dashboard now also the landing route. Reasoning: Dashboard already carried the adaptive "Today's Session" recommender plus stats -- the single most complete answer to "what should I do right now" -- while Curriculum's resume/recommended-next callouts were the only "what's next" signal a learner saw before reaching Dashboard by a second click. Dashboard now surfaces that same resume-lesson callout (reusing `progress.resume_lesson`/`recommended_next_lesson`/`problems_due_for_revision`, the exact fields Curriculum already used -- no new backend data), so the landing page alone answers "what next" instead of requiring a stop at Curriculum first. Curriculum keeps its own copy of the same callout for when a learner lands there directly to browse or plan ahead, and becomes purely the "browse the full 45-day path" page. Problems and Mistake Journal kept their relative order; Scratchpad stayed last as a free-form utility outside the guided learn -> solve -> review loop the other four pages form. `e2e_test.py`'s route assertions were updated in lockstep (Curriculum's content checks moved to `/curriculum`; the resume-callout check now runs against both the new home route and `/curriculum` directly).

**Workflow clarity in the Problem Workspace:** the tab order was Tests/Hints/Trace/Complexity/Approaches/Playground/History; Trace now sits directly after Tests (Tests/Trace/Hints/Complexity/Approaches/Playground/History), matching the actual loop -- write code, run tests, trace a failure, and only reach for hints if still stuck, rather than needing to pass over Hints to get to the tool that's next in the actual workflow. The Trace tab also now explicitly states its relationship to Run: before any test run it says tracing works standalone but is most useful once you've seen a failing case; after a failing run it points at exactly that relationship rather than leaving it implicit. The pre-existing "Inspect this case in the Trace tab" jump from a failing test (already built during the learning-features pass) is the concrete bridge this messaging points at.

**Responsive layouts were redesigned per screen, not shrunk.** The Problem Browser's `<table>` (unusable below its column count's minimum width) became a responsive row list (`.problem-list-row`, `ProblemBrowser.jsx`) that collapses from a 6-column grid to stacked cards under 760px -- same information, restructured, not scrolled sideways. The Problem Workspace's fixed two-column `.workspace-columns` (with a `position: sticky` right column) stacks to one column and drops the sticky positioning under 860px, so the editor and tabs aren't trapped in a half-width sliver on a phone. The sidebar itself collapses from a fixed 220px vertical column to a horizontal, wrapping top bar below 860px rather than disappearing behind a hamburger menu -- appropriate for a five-item nav.

**Fonts are self-hosted (`@fontsource/*` packages, imported in `main.jsx`), not linked from a Google Fonts CDN.** This matches the reasoning already on file for bundling Monaco locally instead of loading it from a CDN (see `monacoSetup.js`): the app is meant to be cloned and run fully offline, and a CDN font link would have quietly broken that for anyone without outbound network access.

**Accessibility:** a single global `:focus-visible` rule (`App.css`) gives every interactive element the same amber focus ring used for trace/inspection focus elsewhere -- keyboard focus legitimately is "the thing being looked at right now." `prefers-reduced-motion` is respected for the sort-bar transition and a new loading-state pulse. The Monaco editor now uses a custom theme (`codeloupe-dark`, defined in `monacoSetup.js`) and IBM Plex Mono instead of the stock `vs-dark` default, so the one place code is actually written matches the code-block styling used to display it everywhere else, rather than reading as an unrelated embedded widget.

Functional Unicode glyphs that aren't decorative (the reset/warning/cycle symbols already in the trace viewer, the existing arrow glyphs) were left alone.

## Teaching system content architecture: concept lessons, not a second curriculum

A structured request to add a real teaching layer -- "Learn -> Understand -> See -> Practice -> Solve -> Test -> Trace -> Review -> Revise" -- arrived immediately after the rebrand/polish pass above, with an explicit tension: the user had just said "no new features, finish and polish," then, moments later, asked for what is unambiguously a large new feature. Their own phrasing ("propose/implement... incrementally," "do not change the curated problem counts or expand the problem bank") pointed at a staged rollout rather than a single massive content dump, so this was surfaced back as a scope/sequencing question rather than assumed: architecture-plus-one-pilot-topic now, full stabilization/docs/deployment work after, full curriculum content only once the pilot's shape is reviewed. This section covers that pilot.

**The pilot is Arrays -> Two Pointers, not an arbitrary starting point.** Days 8, 13, and 14 of the existing 45-day curriculum already teach exactly this sequence -- the curriculum's own first topic and first pattern -- so the teaching system plugs into an already-taught, already-curated sequence instead of sitting off to the side as a disconnected demo. `problems.topic`/`problems.pattern` and `logic/pattern_families.py`'s normalized family names were audited first and reused as the addressable vocabulary (`arrays`, `two-pointer`, and the rest of the 15 existing topic values) rather than inventing a second taxonomy -- a new concept lesson is just a row whose `topic` matches an existing `problems.topic` value, and every problem/day tagged with that topic picks it up automatically.

**Linking to problems and day-lessons is a computed topic-string match, not a join table.** `app.py`'s `_related_concept_lessons()` queries `concept_lessons WHERE topic IN (...)` against whatever topics a problem or day's problems carry, and `_related_problems_for_concept()` does the reverse (optionally narrowed by `pattern_family_for()` for a lesson that targets one specific family within a topic). A hardcoded link table would go stale the moment a new problem, day, or concept lesson is added on its own; deriving the link from vocabulary both sides already share never can. This is also what makes "expand to the rest of the curriculum later" a content-only change: new rows in `db/seed_concepts.py`, no schema or endpoint change, per the explicit "scalable architecture... without redesigning the whole app" requirement.

**Four new tables (`concept_lessons`, `concept_checkpoints`, `concept_practice_exercises`, `concept_lesson_progress`), deliberately separate from the existing day-based `lessons` table**, which keeps meaning what it always meant: a concise per-day mix of Python fundamentals and a pointer at that day's DSA vocabulary (see Day 8/13/14's own `concept_markdown`, one or two sentences each). The teaching system's `what_markdown`/`why_markdown`/`recognize_markdown`/`intuition_markdown`/etc. are the deeper "what is this, why does it work, when do I reach for it" content the day lessons never had room for. Each concept lesson is `kind='topic'` (a broad foundational lesson, e.g. Arrays) or `kind='pattern'` (a specific recognizable technique, e.g. Two Pointers) -- the same two-level structure the user's own brief used (Arrays, then patterns like Two Pointers "connect naturally to relevant problems").

**Pattern-recognition ("when should I use this?") is a first-class field, not folded into general prose**, per the explicit emphasis in the request. `recognize_markdown` gets its own section and its own visual treatment (a teal-accented callout, `.recognize-section` in `App.css`) rather than reading as just another paragraph -- concrete signals (sorted input, comparing two positions, a nested-loop instinct that turns out to have exploitable structure), not just a description of the mechanism.

**Teaching visualizations reuse the existing visualizer components on hand-authored, hand-verified frames -- and stay structurally separate from the trace-your-own-code system, per an explicit constraint.** `ConceptWalkthrough.jsx` steps through a JSON array of `{caption, locals}` frames (`concept_lessons.walkthrough_frames_json`) using the same `ArrayPointerView` component `TraceViewer.jsx` renders real trace steps with, so a learner sees one consistent visual language for "array + pointers" everywhere in the app. It stops there on purpose: this component never calls `/api/.../trace` or touches `sys.settrace`, and has no play/predict-mode/event/line/call-depth chrome, so it can never be mistaken for the real tracer. Every frame is a verified-by-hand trace of the walkthrough's own code actually running on the given input (checked by literally running it, not invented) -- e.g. the two-pointers walkthrough traces `two_sum_sorted([1, 2, 4, 7, 11, 15], 15)` through its real four steps. Codeloupe's actual differentiator -- write your own code, run it, trace what IT did -- still lives only in `TraceViewer.jsx`.

**Checkpoints are lightweight by design, per the explicit "not a generic quiz app" instruction.** `choose_pattern` gets real multiple-choice buttons with immediate right/wrong feedback (`Checkpoint.jsx`) since there's a small fixed set of good answers and a click is more honest than free text; `predict_output`, `spot_bug`, and `complexity` are reveal-then-check, the same interaction `LessonDetail.jsx` already used for its day-1-style prediction questions, rather than a free-text answer grader that would either be trivially gameable or need real NLP-ish matching for little pedagogical gain. `order_steps` is in the schema's `CHECK` constraint for future use but not built (or seeded) in this pass -- a drag-and-drop reordering UI is real added complexity for one more checkpoint shape, and the other four already cover predict/recognize/debug/complexity.

**Practice exercises are deliberately lighter-weight than curated problems**: a prompt, an optional starter stub, a reference solution, an optional hint -- no test harness, no hints ladder, no attempt/mistake tracking. They're meant to be done in the existing Scratchpad (linked, not prefilled -- no new prefill-via-navigation plumbing was built for this pass) before a full curated problem, not a second problem bank.

**A new "Learn" nav slot, not a bolt-on inside Curriculum or individual problem pages.** Concept lessons are a genuinely different content type from the day-based Curriculum (a topic/pattern lesson vs. a day-by-day schedule), and per the explicit "make it obvious Codeloupe is a learning platform, not just a LeetCode-style question list" requirement, that needed one real place to browse all of them -- Dashboard -> Learn -> Curriculum -> Problems -> Mistake Journal -> Scratchpad & Trace, matching the nav structure the request itself suggested. Every other integration point links INTO a concept lesson contextually instead: a problem page shows a "Pattern to know" callout (`ProblemWorkspace.jsx`) and a day lesson shows a "Learn: ..." callout (`LessonDetail.jsx`), both driven by the same `_related_concept_lessons()` helper and both empty (gracefully, not broken) for the 42 of 45 days that don't yet have authored concept content -- exactly the "incrementally" framing the request asked for.

Verified with a dedicated suite (`e2e_teaching_test.py`, 29/29 checks): the Learn hub lists and groups both pilot lessons; every lesson section renders (including that the lightweight `**bold**`/`` `code` `` inline-text convention -- extended this pass from `MultilineText.jsx`'s pre-existing backtick-only support -- renders as real markup, not literal asterisks/backticks); the walkthrough steps through its frames and visibly changes both caption and rendered state; a `choose_pattern` checkpoint gives correct/incorrect feedback; a reveal-style checkpoint shows its answer; a practice exercise reveals its solution; status persists across a reload; a problem page and a day lesson both link in; and Day 1 (no authored concept content yet) shows no broken or empty callout. Full existing regression re-run clean afterward: `test_endpoints.py` (all backend smoke checks, including the new `/api/concepts*` endpoints), and all six pre-existing E2E suites individually against freshly reseeded data (`e2e_test.py`, `e2e_central_workflow_test.py`, `e2e_learning_features_test.py`, `e2e_visualizers_test.py`, `e2e_mistake_journal_test.py`, `e2e_approach_comparison_test.py`) -- zero regressions from adding the new tables/endpoints/nav item.

## Teaching system expansion: batch 1 (Prefix Sums, Strings, Hashing)

With the pilot reviewed and stabilization/docs work complete, the user's own follow-up instruction named an explicit curriculum-ordered expansion list and said to proceed "incrementally and in coherent batches" without waiting for further check-ins. Batch 1 covers items 1-3 of that list (remaining array patterns, Strings, Hashing) -- concretely, Days 9-12 of the curriculum, which is where `problems.topic` already has `prefix-sums`-pattern array problems plus standalone `strings` and `hashing` topic problems sitting unaddressed by the pilot's two lessons. No schema, endpoint, or component change was needed for this batch -- exactly the payoff the pilot's topic-string-match linking design was built for: three new rows in `CONCEPT_LESSONS` (plus their checkpoints/practice exercises) picked up their problem/day links automatically.

**Prefix Sums is `kind='pattern'` under `topic='arrays'`**, same topic as the Arrays lesson, `prerequisite_slugs='arrays'` -- surfacing the one existing ordering bug the pilot's `ORDER BY cl.topic, cl.kind, cl.display_order` had never been exercised against: alphabetically, `'pattern' < 'topic'`, so within the `arrays` group Prefix Sums was sorting ahead of the foundational Arrays lesson it depends on. Fixed with a `CASE cl.kind WHEN 'topic' THEN 0 ELSE 1 END` ordering expression in both `list_concepts()` and `_related_concept_lessons()` (verified via curl and a new hub-ordering assertion in `e2e_teaching_test.py`). Its walkthrough traces `build_prefix_sums([3, 1, 4, 1, 5])` and is the first lesson to render two labeled sequences side by side (`arr` and `prefix`) rather than one -- `ArrayPointerView` already supported this (it maps over every array-shaped local in `locals`), so no visualizer change was needed, only frames with two array keys. Its `spot_bug` checkpoint targets the specific `prefix[left - 1]` bug at `left=0`: valid Python, silently reads `prefix[-1]` (the last element) via negative indexing, and returns a wrong answer with no crash -- picked because it's a real, easy-to-miss beginner trap rather than a contrived example.

**Strings and Hashing are both `kind='topic'`, prerequisite `arrays`.** Strings' walkthrough traces `expand_around_center("babad", 1, 1)` and its common-mistakes section covers the `s += char` in a loop O(n^2) trap (Python strings are immutable, so each `+=` allocates and copies a new string) alongside the odd/even-center-length bug real palindrome code hits. Hashing's walkthrough traces `two_sum([3, 5, 2, 9, 7], 12)` and is the first lesson whose primary data structure (a `dict`) has no dedicated visualizer in `Visualizers.jsx` -- rather than build one (scope creep for a single lesson) or silently drop the dict state (dishonest), `walkthrough_intro_markdown` says plainly that `seen` isn't rendered visually here and that its contents are narrated in each step's caption instead, and every caption does exactly that (`seen = {3: 0}`, etc.). Its `spot_bug` checkpoint covers the check-before-record ordering bug: checking `complement in seen` before writing `seen[n] = i` (not after) is what keeps `target == 2 * n` from wrongly matching an element against itself.

Verified by extending the existing `e2e_teaching_test.py` rather than a new file (12 new checks, 41/41 total): the Learn hub now lists all five lessons in correct topic-before-pattern order; Prefix Sums renders both array sequences with correct labels and its negative-indexing checkpoint explanation; Strings' walkthrough steps through its frames; Hashing's honesty disclaimer and dict-narrating captions both render. Full regression re-run clean via `run_all_tests.sh` (10/10 suites, freshly reseeded before each) -- zero regressions from the three new lesson rows or the `ORDER BY` fix.

## Teaching system expansion: batch 3 (Linked Lists, Fast/Slow Pointers)

Item 5 of the expansion order (Days 25-27). Two lessons, mirroring the Arrays/Two-Pointers pilot's topic+pattern split: `linked-lists` (`kind='topic'`: nodes, traversal, insertion/deletion, in-place reversal, `prerequisite_slugs='arrays'`) and `linked-list-fast-slow` (`kind='pattern'`, `pattern_family='Fast/slow pointers'` -- an existing family rule in `pattern_families.py` that already groups "Floyd's slow/fast pointer" / "fast/slow pointer" / "fast/slow + reversal" under one name, so setting it narrows `_related_problems_for_concept()` to exactly the 3 matching curated problems instead of all 7 linked-list-topic problems, `prerequisite_slugs='linked-lists,two-pointers'` since it's explicitly taught as same-direction two-pointers with an unequal step size).

**First topic whose primary data structure isn't array-shaped -- a real gap in the pilot's walkthrough architecture, not a redesign.** `ArrayPointerView` renders `locals` as boxes in a row; a linked list is a chain of objects connected by `.next`, which the app already has a dedicated renderer for (`LinkedListView`, built for real traces via `nodeGraph.js`'s `collectNodeGraph`). Per the standing instruction to reuse and only minimally refine the walkthrough architecture, `ConceptWalkthrough.jsx` gained a small adapter (`buildLinkedListGraph`): lessons author frames as `locals = {nodes: [{id, val, next}], pointers: [[name, id], ...]}` -- far simpler than hand-building `LinkedListView`'s real `Map`-based graph shape -- and the adapter converts it at render time. `ConceptWalkthrough` picks `LinkedListView` vs `ArrayPointerView` based on `topic === 'linked-lists'` plus the frame actually having a `nodes` array, so every other lesson's rendering path is untouched.

**Bug found and fixed during this batch: `pointers` had to become an ordered list of `[name, id]` pairs, not a `{name: id}` object.** `LinkedListView` picks its chain's starting node from the first root with a non-null id (absent a `head`-named one) -- the design here deliberately relies on that, using pointer order to control which side of a reversal renders as the "main chain" versus the "not yet relinked" orphans. Authoring `pointers` as a plain dict broke this silently: Flask's JSON provider sorts object keys alphabetically before serializing the API response, so `{"prev": ..., "curr": ...}` always reached the browser as `curr` first regardless of authoring order, putting the wrong side of the reversal in the main chain. Confirmed via screenshot before the fix (the reversal's "already reversed" node showed as the orphan, its still-linked remainder as the main chain -- backwards) and after (correct). JSON array order survives `sort_keys` serialization; object key order does not -- the fix and the reasoning are both commented in `seed_concepts.py` and `ConceptWalkthrough.jsx` so it isn't rediscovered the same way for Trees/Graphs later.

**The reversal walkthrough's mid-scan frames are the first to show `LinkedListView`'s orphan handling in a lesson**, and on purpose: as `reverse_list` runs, the growing `prev` chain and the still-linked-but-not-yet-relinked remainder under `curr` are genuinely two separate reachable structures for one step at a time, and the lesson's own captions call this out explicitly ("that's not a rendering glitch") rather than treating it as a wrinkle to hide. The fast/slow walkthrough traces cycle detection on a list that loops back to its *second* node (not the first), so the visualization's cycle indicator and its "no longer referenced by either pointer" orphan (the original head, once both pointers have moved past it) both get exercised for real, not just the common self-loop case.

Verified by extending `e2e_teaching_test.py` a third time (12 new checks, 60/60 total): the hub lists eight lessons across six topic groups; the linked-list walkthrough renders via `.ll-chain` (never `.seq-boxes` -- confirms the adapter actually switched renderers, not just added one alongside); the split-chain frame's "not reachable" wording renders; the final frame's chain reads `3, 2, 1` in true document order (a real reversal, not a relabeled display); both prerequisite links render on the fast/slow lesson; the cycle indicator and stacked pointer chips render at the moment of detection; Day 27 links to both lessons. Also fixed a latent collision in the pilot's own original hub-navigation check: `page.get_by_role("link", name=re.compile("Two pointers"))` started matching the *Fast/slow pointers* card too, since that card's own summary text begins "Two pointers moving through..." -- a fuzzy text match against a link's full accessible name (title *and* summary) was never safe once enough lesson summaries existed to legitimately reference other lessons' names; switched to an exact `href`-based selector. Full regression clean via `run_all_tests.sh` (10/10 suites, freshly reseeded each).

## Teaching system expansion: batch 4 (Stacks, Queues)

Item 6 of the expansion order (Days 28-29). Unlike Linked Lists/Fast-Slow, this batch stayed at ONE lesson per topic rather than splitting off a pattern lesson for the monotonic stack/deque technique -- both topics have only 4 curated problems each, not enough backing to justify a whole second lesson the way Two Pointers (7+ problems) or Fast/Slow (3, still deemed worthwhile given how distinct and heavily-tested the technique is) did. ## Teaching system expansion: batch 7 (Sorting, Divide-and-conquer sorting)

Item 9 of the expansion order (Days 17-20). Days 17-18 (bubble sort, insertion sort -- both `O(n^2)`) and Days 19-20 (merge sort, quicksort -- both `O(n log n)` divide-and-conquer) are the curriculum's own conceptual split, and it matches `pattern_families.py`'s own pre-existing two-family distinction for `topic="sorting"` ("Sorting fundamentals" vs "Divide and conquer sorting") exactly -- so the batch became `sorting` (`kind='topic'`, `prerequisite_slugs='arrays'`) and `divide-and-conquer-sorting` (`kind='pattern'`, `pattern_family='Divide and conquer sorting'`, `prerequisite_slugs='sorting,recursion'` -- the first lesson in this expansion to declare two comma-separated prerequisites, since divide-and-conquer sorting genuinely depends on both the simpler sorts AND recursion, which batch 5 already covered). `pattern_family` narrows the pattern lesson's related problems to the 2 curated divide-and-conquer problems (merge sort, quicksort), while the topic lesson (no `pattern_family`) naturally links all 4.

**The divide-and-conquer walkthrough deliberately visualizes quicksort's partition step, not merge sort's merge step -- a hazard caught during design, before any screenshot.** Merging reads from TWO same-length arrays (`left`, `right`) with independent index variables `i` and `j`. `ArrayPointerView` computes "is this int a valid pointer" independently per rendered sequence (line 56 of `Visualizers.jsx`: `intVars.filter(([, v]) => v >= 0 && v < arr.length)`, scoped only by numeric range, not by which array the variable is semantically about) -- so with `left` and `right` both length 3, `i` (meaningful only on `left`) would ALSO render as a chip on `right`, and `j` (meaningful only on `right`) would ALSO render on `left`. This is the same class of hazard the Stacks/Queues/Recursion/Backtracking batches (4-5) hit and worked around by dropping an irrelevant local from view -- but dropping either `i` or `j` here would have gutted the actual point of a merge visualization (watching both pointers advance independently). Unlike Prefix Sums' `arr`/`prefix` pair, where a SHARED index is intentionally meaningful on both sequences, `i` and `j` here are never meaningful on the other array, so there was no safe way to show both pointers on both arrays simultaneously. Quicksort's partition works on a SINGLE array with `i`/`j` as genuinely single-array pointers (exactly the shape every successful walkthrough so far has used -- Arrays' `write`/`read`, Binary Search's `lo`/`hi`/`mid`), sidestepping the hazard entirely. It's also the more forward-looking choice: Day 20's own pre-existing curriculum content already calls out that "partition logic reappears in quickselect-style problems," which this batch's own practice exercise (`quickselect`) then builds on directly, reusing the lesson's own `partition()` function.

**A screenshot of Day 19's own pre-existing `example_code` (authored as part of the original 45-day curriculum, unrelated to this batch) independently confirmed the hazard was real, not a hypothetical worry**: Day 19 already shows a `merge(left, right)` helper using exactly `result, i, j = [], 0, 0` with `left`/`right` both being scanned by separate indices -- the precise shape that was ruled out for the walkthrough. Seeing the curriculum's own reference code use that shape (and knowing it would have produced misleading chips if walked through with `ArrayPointerView`) reinforced that the partition-instead-of-merge decision addressed a real rendering problem, not a theoretical one.

**Both walkthroughs continue the "why while, not if" recurring theme**: insertion sort's `key=1` step needs three shifts in a row to reach the front of the array, explicitly captioned as "exactly why this has to be a while loop, not an if" -- the same beat as Sliding Window's double-shrink, Stacks/Queues' double-pop, mirrored here for a fourth (and, cumulatively across all seven batches, now well-established as a genuinely recurring amortized-algorithm pattern rather than incidental phrasing).

**Two `spot_bug` checkpoints target real, verified-by-execution silent-failure bugs, not contrived ones.** The sorting lesson's bug (`while arr[j] > key` missing `j >= 0`) was run against `[5, 2, 4, 1, 3]` and confirmed to silently read from the END of the array via Python's negative-index wraparound for several steps (corrupting the shift with unrelated elements) before eventually raising `IndexError` once `j` passed `-len(arr)` -- verified with printed intermediate state, not assumed. The divide-and-conquer lesson's bug (omitting `partition`'s final pivot-placement swap) was run against 50 random arrays through a full recursive quicksort and found to silently produce a wrong (unsorted) result on 39 of them while happening to sort correctly on the other 11 (whenever the pivot already belonged at `hi`) -- exactly the "passes some cases, fails others" profile that makes a bug worth a dedicated checkpoint, and the checkpoint's own choice list is followed by the lesson's own correct `walkthrough_code`, so a learner can directly diff the buggy version against the working one.

Rather than force a day's lesson to only cover one family's problems (which would misrepresent what the day actually teaches), `graphs`, `graph-bfs`, and `graph-dfs` all leave `pattern_family` unset -- the same tradeoff batches 8 and 9 already established for BSTs and top-k-heap. `graph-shortest-paths` is the one lesson this batch that DOES narrow: its `pattern_family="Graph shortest paths"` cleanly matches under the existing rules and surfaces a genuinely coherent "Apply it" list (Network Delay Time, Rotting Oranges, Word Ladder, Clone Graph -- 4 of the topic's 9 curated problems), so there was no reason to leave it unnarrowed just for consistency with the other three.

**Two different node shapes were needed, and the real trace system (`detect.js`'s `detectPrimaryView`) already draws exactly this same distinction** -- a node-and-edge graph (`graphKind === "graph"`, using `neighborIds`) versus a grid (`topic === "graphs" && hasGridLocal(locals)`). `ConceptWalkthrough.jsx` mirrors that split: a new `buildGraphNodeGraph` adapter (parallel to `buildTreeGraph`/`buildLinkedListGraph`, converting an authored `{nodes: [{id, val, neighbors: [id, ...]}], pointers: [[name, id], ...]}` shape into `GraphNodeView`'s `{nodes: Map(id -> {fields, neighborIds}), roots}`) for `graphs`, `graph-dfs`, and `graph-shortest-paths`; and `GridGraphView` used directly with no adapter (same as `HeapView` in batch 9) for `graph-bfs`'s grid walkthrough. Unlike `TreeView`/`LinkedListView`, `GraphNodeView` has no "anchor" node the whole layout depends on -- it lays out every node in `nodes` at a fixed angle around a circle and draws edges from `neighborIds` (deduped, so an edge only needs declaring from one end) -- so `buildGraphNodeGraph` doesn't inherit the older adapters' ordered-roots-list requirement; `pointers` here is purely additive colored tags.

**`graph-shortest-paths` (Dijkstra) needed to show a piece of state neither existing visualizer renders: each node's live shortest-distance-so-far.** Rather than build a new side panel, the lesson encodes `dist` directly into each node's own label text per frame (e.g. `"A d=3"`, updated to `"A d=3*"` once finalized) -- the same "narrate what the view can't show" tradeoff `graph-bfs` makes for its queue contents (mentioned only in captions, not rendered) and `graph-dfs` makes for `on_stack` (rendered as pointer tags instead, since it's a set of *nodes* rather than a scalar value). This keeps the visualizer surface unchanged while still making Dijkstra's core moment -- node A relaxed twice, `4` then a cheaper `3`, before ever being finalized -- directly visible frame to frame.

**All four walkthrough traces, all three `spot_bug` checkpoints' buggy code, and all four practice-exercise solutions were verified by actual execution before authoring**, continuing this expansion's standing discipline. Two bugs are worth calling out specifically because the verification changed what got written: the `graph-bfs` "mark visited at pop time" version was hypothesized to be broken, but execution showed it's merely *wasteful* (8 enqueue events instead of 5 for the same correct final count of 5) rather than incorrect, so the checkpoint and lesson text were written to teach that distinction honestly rather than overstate it as a correctness bug. The `graph-dfs` "check `nxt in visited` instead of `nxt in on_stack`" version was confirmed via execution to produce a genuine false positive on an acyclic diamond graph (`D->A->C, D->B->C` -- no real cycle, but the buggy version reports `True`), and the `graph-shortest-paths` "only relax a neighbor the first time it's seen" version was confirmed to produce genuinely wrong distances (`A=4, C=6` instead of the correct `A=3, C=4`) -- both real correctness bugs, not just inefficiencies.

Verified by extending `e2e_teaching_test.py` a tenth time (24 new checks, 174/174 total): each lesson's walkthrough renders via the correct visualizer (`GraphNodeView`'s `.graph-node` for `graphs`/`graph-dfs`/`graph-shortest-paths`, `GridGraphView`'s `.grid-cell` for `graph-bfs`, each confirmed mutually exclusive against every other renderer's marker class); `graph-dfs`'s fourth frame shows all four `on_stack` pointer tags before its fifth frame's caption identifies the back edge and reports a cycle; `graph-shortest-paths`'s live `dist` labels render (`"d=0"` present in the walkthrough's text) and its fourth frame's caption explains skipping the stale finalized entry for A; `graphs` (unnarrowed) shows all 9 topic-level curated problems while `graph-shortest-paths` (narrowed) shows exactly 4; Days 35 through 38 each show callouts for all four graph lessons. Also visually confirmed via Playwright screenshot (all four lessons, mid-walkthrough) with zero console errors -- including catching and correcting a test-authoring mistake along the way, where an initial screenshot pass navigated with plain paths (`/learn/graphs`) instead of the app's `HashRouter` routes (`/#/learn/graphs`), silently rendering the Dashboard instead of erroring; fixed before it could be mistaken for an app bug. Full regression clean via `run_all_tests.sh` (10/10 suites, freshly reseeded each).

## Teaching system expansion: batch 11 (Dynamic Programming, 1D DP, 2D DP) -- the final batch

Item 13 -- the LAST item -- of the curriculum-ordered expansion (Days 39-42). Three lessons, not four, despite four curriculum days: this is the one batch in the whole expansion where the day-to-lesson mapping is deliberately NOT 1:1. Day 39 ("DP I: overlapping subproblems, memoization vs tabulation") is its own topic lesson (`dynamic-programming`), directly paying off Day 23's own "naive Fibonacci is slow" cliffhanger per its concept_markdown. Days 40 ("1D DP: decision at each step") and 41 ("coin change, LIS intro") both fall under `pattern_families.py`'s SAME existing rule (`"1d" in pattern -> "1D dynamic programming"`) and, more to the point, teach the identical underlying shape -- `dp[i]` built from a decision over already-computed earlier values -- just with different per-step recurrences (House Robber's fixed skip-or-take pair vs Coin Change's try-every-coin vs LIS's compare-against-every-earlier-index). That's a difference in RECURRENCE, not in STRUCTURAL PATTERN, so both days share one `dp-1d` lesson rather than being force-split -- directly mirroring batch 7's own precedent, where Sorting's four curriculum days (17-20) became just two lessons, grouped by technique-similarity rather than day-count. Day 42 ("2D DP intro") gets its own lesson (`dp-2d`): two coordinates instead of one is a genuine structural generalization, matches `pattern_families.py`'s separate "2D dynamic programming" rule cleanly, and closes out the expansion order.

**`DPTableView` is the first visualizer this whole expansion has needed that ISN'T satisfied by just the current frame's `locals`.** Its cell-level diff highlighting (which cell just changed, so a learner can see exactly which subproblem their code just solved) calls `findPreviousValue(steps, index, name)`, which walks backward through the FULL trace history looking for a named local's previous value -- every other view used across ten prior batches (`ArrayPointerView`, `LinkedListView`, `TreeView`, `HeapView`, `GridGraphView`, `GraphNodeView`) only ever needed the single current frame in isolation. No new data-shape adapter was needed, though -- `frames[i].locals` (already `ConceptWalkthrough.jsx`'s own state shape) matches exactly what `findPreviousValue` expects from a real trace's `steps[i].locals` -- so the only change was a new branch threading this component's own `frames` and `index` state through as `steps`/`index` props, rather than a `buildXGraph`-style conversion function. Verified visually via screenshot: the diff-highlighted cell renders in the same amber token Codeloupe reserves site-wide for current-inspection-focus, exactly as intended, for both the 1D (`dp-1d`) and 2D (`dp-2d`, reusing `DPTableView`'s `is2D` branch with no additional wiring) cases.

**All three walkthrough traces, all three `spot_bug` checkpoints' buggy code, and all three practice-exercise solutions were verified by actual execution before authoring**, closing out the expansion's standing discipline one final time. One number was specifically worth verifying rather than guessing: naive recursive `fib(6)` calls `fib(2)` exactly 10 separate times (confirmed via an instrumented call-counter), not some rounder-sounding guess -- the `dynamic-programming` lesson's own closing frame states this exact, execution-confirmed number. The `dp-1d` spot_bug (`dp[i] = max(dp[i-1], nums[i])`, missing the `dp[i-2] +` term) was confirmed to return `9` instead of the correct `12` on `nums=[2,7,9,3,1]` -- a real correctness bug, not just an inefficiency. The `dp-2d` spot_bug (computing the first column inline as `dp[r-1][c] + 1` instead of leaving it at its base-case `1`) was confirmed to produce a wrong, inflated grid (`[[1,1,1],[2,3,4],[3,6,10]]` instead of the correct `[[1,1,1],[1,2,3],[1,3,6]]`).

Verified by extending `e2e_teaching_test.py` an eleventh time (33 new checks, 207/207 total): each lesson's walkthrough renders via `DPTableView`'s `.dp-cell` elements (confirmed absent from every other renderer's marker class, and vice versa); the fourth frame of each of the three walkthroughs highlights exactly one `.dp-cell-changed` cell with the correct execution-verified value (`2` for Fibonacci's `dp[3]`, `11` for House Robber's `dp[2]`, `3` for Unique Paths' `dp[2][1]`); `dynamic-programming` (unnarrowed) shows all 10 topic-level curated problems while `dp-1d` (narrowed to "1D dynamic programming") shows 5 and `dp-2d` (narrowed to "2D dynamic programming") shows 3; Days 39 through 42 each show callouts for all three DP lessons. Also visually confirmed via Playwright screenshot (all three lessons, mid-walkthrough) with zero console errors. Full regression clean via `run_all_tests.sh` (10/10 suites, freshly reseeded each) -- after one confirmed flake (the Learn hub's card-count check failed once when run back-to-back with nine other Playwright suites under load, then passed cleanly on immediate re-run twice in isolation and once more in a full clean re-run of the whole suite; treated as environmental flakiness, not a regression, since the underlying API and DB were independently confirmed to already report the correct count of 28 at the time of the failure).

**This closes the curriculum-ordered expansion.** All thirteen items of the original expansion order (Arrays foundations through Dynamic Programming) now have concept lessons, bringing the teaching system from the pilot's original 2 lessons to 28, spanning every major topic the 45-day curriculum covers. At the time this batch closed, the two integration points named in the original brief -- wiring the teaching system into Mistake Journal pattern-level revision, and into Today's Session recommendations -- were still deliberately deferred (see the next section for why that changed).

## Known limitations, stated up front (for the eventual README)

The sandbox is appropriate for trusted, single-user code, not hostile input. The complexity estimator is a teaching aid, not a certifier. The trace visualizer's per-topic renderers cover the specific data shapes the curriculum uses, not arbitrary Python objects. The problem bank is curated and intentionally not comprehensive. The teaching system covers twenty-eight concept lessons (Arrays, Two Pointers, Prefix Sums, Strings, Hashing, Sliding Window, Linked Lists, Fast/Slow Pointers, Stacks, Queues, Recursion, Backtracking, Binary Search, Binary Search Variants, Sorting, Divide-and-conquer sorting, Trees, Binary Search Trees, Tree BFS, Heaps, Top-K with a bounded heap, Graphs, Graph BFS, Graph DFS, Dijkstra's algorithm, Dynamic programming, 1D DP, 2D DP -- the reviewed pilot plus expansion batches 1-11), spanning every topic in the 45-day curriculum's original expansion order. This is not a partial rollout awaiting future batches -- the curriculum-ordered expansion described at the top of this section is complete.

## Final stabilization: closing the Mistake Journal / Today's Session integration gap

The two integration points deferred above were revisited once, deliberately, after the curriculum expansion closed and the product moved into a final stabilization pass -- not as scope creep, but because the earlier "chose not to build" reasoning was explicitly conditional on it: *if a clean implementation isn't justified, leave the gap documented rather than forcing it.* With all 28 lessons in place (versus the 2-lesson pilot the original deferral was weighed against), the honest answer changed.

Both turned out to need **zero new taxonomy or inference**. `logic/pattern_families.py` gained one function, `concept_lesson_for_family(conn, topic, pattern_family)` -- the exact reverse of `app.py`'s existing `_related_problems_for_concept` (a lesson "covers" a `(topic, pattern_family)` pair when `lesson.topic` matches and `lesson.pattern_family` is either `NULL`, meaning whole-topic coverage, or equals the family exactly; never a fuzzy match, and it returns `None` rather than guess when nothing covers it). Every caller treats `None` as "omit the suggestion," never as a broken link or a fallback guess -- the same "unclassified is better than wrong" discipline `logic/mistakes.py` already applies to mistake categories now applies to lesson suggestions too.

Three call sites, all additive fields on responses that already existed (no new endpoints):
- `GET /api/mistakes/journal` -- each entry gains `related_lesson` (`{slug, title}` or `null`), rendered in `MistakeJournal.jsx` as a one-line "Revise: <lesson>" link right under the entry it explains.
- `GET /api/progress` -- `pattern_weaknesses` entries gain the same `related_lesson` field, rendered in `Dashboard.jsx`'s "Weakest patterns" section as an inline "revisit lesson" link.
- `logic/practice_session.py`'s `build_practice_session` gains one new candidate slot, `revisit_lesson`: when the session's recurring-mistake family resolves to a lesson the learner hasn't already marked completed/known, it's offered as a fifth "Today's session" item (bumping `MAX_ITEMS` 4 -> 5, so this is additive to the existing four slots, never a replacement for any of them). `Dashboard.jsx` links a `revisit_lesson` item to `/learn/<slug>` instead of `/problems/<slug>`; every other item kind is unaffected.

Every one of these three is a plain "may or may not be present" field/slot -- there's no new confidence language claiming more certainty than the classifier already has, and normal navigation is untouched (the Learn hub, every problem, and every lesson remain reachable exactly as before regardless of what any recommendation shows). Verified end-to-end against a live backend (deliberately logging two real "Logic errors" mistakes on the same pattern family via `POST /api/attempts`, confirming `related_lesson`/`revisit_lesson` appear correctly in the raw API responses, then again visually in the running UI via Playwright screenshot of both the Dashboard and Mistake Journal pages) and via the full regression suite (`run_all_tests.sh`, 10/10 suites, DB freshly reseeded).

While auditing the surrounding Dashboard/Learn relationship for this same stabilization pass, a separate, real disconnect turned up: the Dashboard's "Lesson progress" section only ever reflected the 45-day curriculum's `lesson_status_counts` -- Learn-hub concept-lesson progress (a genuinely separate track, its own `concept_lesson_progress` table) had no visibility on the Dashboard at all, even though marking a concept lesson in-progress or complete is a normal, encouraged action from the Learn hub. Fixed the same way: `/api/progress` gained a sibling `concept_lesson_status_counts` field (never merged into the curriculum's own counts -- they're two different 45-vs-28 denominators and folding one into the other would misrepresent both), and the Dashboard now renders it as its own "Concept lessons" section, reusing the exact same status-bar/legend styling the curriculum section already uses, right next to it, retitled "Curriculum progress" for clarity now that there are two.

Confidence, not certainty, throughout: every mistake category the classifier assigns is `likely_issue` at most (per `logic/mistakes.py`'s own long-standing discipline), so a `related_lesson`/`revisit_lesson` suggestion built on top of that category inherits the same honesty -- it's a plausible next step, shown with its reasoning in plain language, never framed as a diagnosis or a required path.
